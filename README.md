# Notification Preferences Service

Сервис управления предпочтениями уведомлений для платформы, которая отправляет пользователям уведомления по нескольким каналам: email, SMS, мессенджеры, пуши.

## Функциональность

Сервис предоставляет единый источник правды для управления предпочтениями уведомлений с учётом:

1. **Дефолтных настроек** для новых пользователей
2. **Индивидуальных настроек** пользователя по типам уведомлений и каналам
3. **Глобальных политик** (например, запрет определённого типа уведомлений по региону)
4. **Quiet hours** в заданной таймзоне
5. **Идемпотентность** операций изменения настроек

## Технологический стек

- **TypeScript** - строгая типизация всего backend-кода
- **Node.js** + **Express** - серверная часть
- **PostgreSQL** + **TypeORM** - хранение данных
- **Jest** - тестирование
- **Docker** + **Docker Compose** - контейнеризация
- **Zod** - валидация данных
- **date-fns/date-fns-tz** - работа с датами и таймзонами

## API Endpoints

### 1. Получение предпочтений пользователя
```
GET /api/v1/users/:id/preferences
```

### 2. Изменение предпочтений пользователя
```
POST /api/v1/users/:id/preferences
```
Тело запроса:
```json
{
  "preferences": [
    {
      "notificationType": "marketing_email",
      "channel": "email",
      "enabled": false
    }
  ],
  "quietHours": {
    "enabled": true,
    "timezone": "Europe/Moscow",
    "startHour": 22,
    "endHour": 8,
    "applyToNotificationTypes": ["marketing_push", "marketing_email"]
  }
}
```

### 3. Проверка возможности отправки уведомления
```
POST /api/v1/evaluate
```
Тело запроса:
```json
{
  "userId": "user-1",
  "notificationType": "marketing_email",
  "channel": "email",
  "region": "EU",
  "datetime": "2026-05-21T21:30:00Z"
}
```
Ответ:
```json
{
  "decision": "deny",
  "reason": "blocked_by_global_policy"
}
```

### 4. Управление глобальными политиками
```
GET /api/v1/policies
POST /api/v1/policies
```

### 5. Health check
```
GET /api/v1/health
```

## Запуск проекта

### Способ 1: Docker Compose (рекомендуется)

1. Убедитесь, что установлены Docker и Docker Compose
2. Клонируйте репозиторий
3. Запустите приложение:

```bash
docker-compose up -d
```

Приложение будет доступно по адресу: http://localhost:3000

### Способ 2: Локальная разработка

1. Установите PostgreSQL и создайте базу данных:
```bash
createdb notification_preferences
```

2. Установите зависимости:
```bash
npm install
```

3. Создайте файл `.env` на основе `.env.example`:
```bash
cp .env.example .env
```

4. Запустите приложение в режиме разработки:
```bash
npm run dev
```

Или соберите и запустите в production режиме:
```bash
npm run build
npm start
```

## Тестовые сценарии

Проект включает тесты для всех ключевых сценариев:

1. **Дефолтные настройки для нового пользователя** - проверка, что новый пользователь получает корректные дефолтные настройки
2. **Изменение настроек пользователем** - проверка обновления предпочтений и идемпотентности операций
3. **Влияние quiet hours** - проверка блокировки уведомлений в quiet hours с учётом таймзоны
4. **Влияние глобальных политик** - проверка приоритета глобальных политик над пользовательскими настройками
5. **Валидация входных данных** - проверка корректной обработки невалидных данных

## Основные решения и особенности

### 1. Типизация
- Использованы TypeScript enum для `NotificationType`, `Channel`, `Region`
- Строгая типизация всех DTO и доменных объектов
- Валидация входных данных с помощью Zod

### 2. Работа с временем
- Использование IANA timezone для quiet hours
- Корректная обработка интервалов, переходящих через полночь
- Конвертация времени в таймзону пользователя при проверке quiet hours

### 3. Идемпотентность
- Операции обновления настроек используют `upsert` (create or update)
- Повторное применение одной и той же команды не меняет состояние

### 4. Масштабируемость
- Чистая архитектура с разделением ответственности
- Интерфейсы для всех репозиториев
- Легко заменить реализацию хранилища (TypeORM → другой ORM)

### 5. Observability
- Логирование ключевых событий (изменения настро��к, решения allow/deny)
- Health check endpoint
- Request ID для трассировки
- Graceful shutdown

## Что можно улучшить для production

1. **Миграции базы данных** - добавить систему миграций (TypeORM migrations)
2. **Кэширование** - добавить Redis для кэширования часто запрашиваемых настроек
3. **Метрики** - добавить Prometheus метрики для мониторинга
4. **Аутентификация/авторизация** - добавить JWT токены для защиты API
5. **Конфигурация** - использовать более продвинутую систему конфигурации
6. **Рейт-лимитинг** - защита от DDoS атак
7. **Документация API** - добавить Swagger/OpenAPI документацию
8. **Логирование** - настроить структурированное логирование (JSON) и отправку в ELK
9. **Тестирование** - добавить нагрузочное тестирование и E2E тесты
10. **Мониторинг** - добавить алертинг и дашборды
